\section{Architectural Overview and Data Flow}
\label{sec:architectural-overview}

SSL Guardian follows a data-intensive, component-based architecture that
separates acquisition, dataset maintenance, analytical processing, application
services, and presentation. These components execute independently and
communicate primarily through persisted certificate and analytical data.
Figure~\ref{fig:overall-architecture} presents the end-to-end architecture.

Initial acquisition begins with a domain dataset. Concurrent workers claim
domains, establish TLS connections, retrieve peer certificates, invoke the
certificate parser, enrich the resulting records, and store them in the main
dataset. CT-assisted maintenance provides a second input path. Observed domains
are classified as possible renewals or new discoveries, crawled through the
same acquisition capability, and incorporated after successful processing.

Analytical processing transforms the main dataset into six materialized result
families covering validity, geography, signatures and hashes, SANs, shared
keys, and Certificate Authorities. Detailed certificate views, selected
counts, and time-series operations can also query the main dataset directly.
The application service combines these sources, optionally reuses cached
responses, and returns structured results to the dashboard.

Data passes through three logical lifecycle groups, illustrated in
Figure~\ref{fig:logical-data-model}. Staging records retain CT observations,
task states, temporary crawl results, and recovery information. Canonical
certificate records form the primary analytical dataset. Materialized results
contain per-scope summaries and shared-key group documents used by analytical
views.

The system uses one main analytical dataset while exposing global and
country-level logical scopes. During acquisition, the final domain label is
stored as a scope value. Global analysis omits this filter, whereas a
country-level request selects records and materialized results associated with
the configured scope. This classification represents domain namespace rather
than verified server location, issuer jurisdiction, or certificate-subject
geography.

\section{Indexing, Caching, and Request Processing}
\label{sec:index-cache-strategy}

Indexes support the principal access patterns for scope, domain, certificate
identity, public-key fingerprints, validity dates, cryptographic attributes,
issuer information, SANs, certificate-quality flags, and leaf
classification. Analytical result documents are indexed by scope and by the
feature-specific fields required for sorting and filtering. Materialization
reduces repeated aggregation for frequently requested summaries, while
pagination and bounded reference lists limit response size.

The optional cache stores serialized analytical responses under keys that
include the active scope and normalized request parameters. If caching is
unavailable, the request continues through the data-access path. This makes the
cache an optimization rather than a required source of correctness.

\section{Deployment and Architectural Boundaries}
\label{sec:architectural-constraints}

The developed platform is configured as a locally operated research system.
MongoDB is the primary shared store, Redis is optional, and the CT service and
certificate parser operate as supporting processes. No production cluster or
multi-tenant deployment is assumed.

Several boundaries affect interpretation. Scope selection is maintained as
shared application state and therefore requires redesign for strongly isolated
concurrent users. Certificate acquisition disables normal trust and hostname
validation because the objective is to observe presented certificates.
Temporary dataset updates and analytical refresh operations do not share a
single transaction, so recovery is provided at individual stages rather than
as a global exactly-once guarantee. These limitations are considered further
in Chapter~\ref{chap:verification-security-discussion}.
